DNS 延迟实测与最优方案

数据来源：本机直连实测（绕开代理），2026-11-21 凌晨。测量脚本 tools/bench_dns.py，可复现。

一、实测：每条通道到底多快

通道首包（含 TLS 握手）复用连接后判断
阿里 DoH31–38 ms9.4 ms主力
腾讯 DoH58–61 ms16 ms备用
360 DoH121 ms—不推荐
阿里 DoT90 ms长连接后更低次主力
腾讯 DoT60 ms长连接后更低次主力
CF 公共 DoH失败—不可用
自建 Worker DoH失败—不可用（本网络）
CF DoT432 ms—只做兜底
自建 Gateway DoT477 ms—只做兜底
最关键的发现
阿里 DoH：首包 38 ms → 复用后 9.4 ms，快了 4 倍。
也就是说延迟的大头不是“哪家 DNS”，而是 每次重新做 TLS 握手。 换服务商最多省 20 ms，把连接复用做对能省 28 ms。

二、结论：延迟结构是这样的

  • 0 ms：本地规则命中（广告域直接返回 0.0.0.0）+ 缓存命中（TTL 内不查上游）
  • 9–16 ms：国内 DoH/DoT 长连接复用（这是真实可达的底数）
  • 430–500 ms：CF 系通道（本网络下），只配当兜底，不能当入口
所以“最低延迟”的实现顺序是：先本地短路，再缓存，再复用连接，最后才是选哪家。选服务商是最后一步，不是第一步。

三、落地配置

1. 本机 / 路由器（aiodns，仓库已改好）

aiodns \
  --upstream tls://dns.alidns.com:853 --upstream tls://dot.pub:853 \
  --timeout 1 \
  --http3 \
  --cache \
  --refuse-any
  • --timeout 1：上游卡住 1 秒就切下一个。原来 3 秒，一次抖动就拖垮整页加载
  • --http3：DoH 走 QUIC，少一个往返；上游不支持会自动降级 HTTP/2
  • 两个 DoT 上游常驻长连接，比每次新建快一个数量级

2. Android（系统级 Private DNS，最省事）

dns.alidns.com

系统级 DoT，常驻连接，实测 20 ms 内。不要填 CF 的地址，国内会 400 ms 以上。

3. AdGuard Home / 软路由

  • 上游填 https://dns.alidns.com/dns-query 或 tls://dns.alidns.com:853
  • 开启 缓存，并把 乐观缓存（如果有）打开：TTL 过期先返回旧值再后台刷新
  • 规则加载 subs/lite/adguard.txt 或 subs/mid/adguard.txt，命中即本地返回，0 ms

4. 什么时候才用 CF

  • 不要把 CF DoH/DoT 当查询入口——本网络 430–500 ms，是主力的 30 倍
  • CF 只做两件事：规则分发（raw / Pages / CDN）和 备用兜底
  • 自建 Worker 的作用是“国内 DoH 全挂时还能解析”，不是“更快”

四、为什么 CF 在这条网络上就是慢

CF 的 anycast 节点对国内用户经常落到境外或拥塞节点，TLS 握手 + 首包就要 400 ms 以上；workers.dev 域名还会被网关干扰。这不是配置问题，是链路拓扑问题，优化不动，只能降级为兜底。

五、还能再压的余量

  • 预热：仓库已加 keepalive.yml，每 10 分钟打一次自建 DoH，避免冷启动（CF Worker 空闲后会回收 isolate）
  • TTL 调大：被拦截域返回较长 TTL，客户端不会反复问同一个域
  • EDNS 不带：少一次策略分支，也少泄露信息
  • 并发竞速：客户端同时向阿里+腾讯发首包，谁先回用谁（dnsproxy 的 parallel 模式）
复现方法：python3 tools/bench_dns.py --rounds 5；连接复用测试见同目录脚本内的 keep-alive 段。
